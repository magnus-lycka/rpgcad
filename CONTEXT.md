# RPGCAD context

RPGCAD lets a Traveller Referee develop their own floor plans through an agent, with minimal delay between an instruction and its visible result. In Edit mode the user is the Designer; in Play the user is the Referee. These name activities, not separate accounts or permissions. The Designer supplies the design intent. The agent translates it into geometry, clarifies missing design choices, and inspects the rendered result.

## Visual feedback in the existing conversation

The Designer draws freehand marks on the current plan, then writes the instruction in this chat. There is no browser instruction box or submit action. Pen-up, undo and clear automatically save the current marks through `/sketch`, scoped by the drawing URL's `plan` and `level` selectors. For a layout instruction, read the latest marks on the selected plan and level before interpreting the chat text; the marks supply spatial context, not instructions by themselves. Do not run a background interpreter or require another chat message to submit them.

Carry the drawing URL's `plan` and `level` selectors through the feedback loop. Read `GET /plan?plan=<id>` to locate the selected level's authoritative `model` path (relative to the server's prototype directory), then read `GET /sketch?plan=<id>&level=<id>`. An omitted level selects that plan's first level. Legacy URLs without `plan` select the existing building: `GET http://127.0.0.1:8765/sketch?level=below` reads its lower floor, and `/sketch` reads its ground floor.

Pending nonempty strokes accompany the user's current chat instruction. Inspect their model coordinates and saved model/view, edit that selected level's authoritative model, then `PATCH /sketch` with the same selectors and the record's `submittedAt`, `status: "applied"` and a short `reply`. The browser clears only the acknowledged marks; newer strokes must not be consumed accidentally. Empty or already-applied records do not supply a new sketch. Keep responses and edits prompt: routine implementation checks belong outside this drawing feedback loop.

## Current state

The throwaway prototype uses authoritative JSON model files, a Python standard-library loopback server, and browser-side JavaScript/SVG rendering. One server serves a library of plans and their levels, selected with `?plan=<id>&level=<id>`. Without a library record, the existing plan manifest supplies the Referee building with its ground level and two lower levels (`?level=below` or `?level=below-2`). This is an experiment, not a settled production architecture.

The current model is the Referee's building, developed interactively in this conversation. Preserve it when changing the prototype. It includes four corner rooms with ceiling hatches and wall-mounted step irons, two lifts, closed doors, and a spiral staircase with a platform. The level immediately below now starts with aligned copies of the two lifts and staircase/platform, with the stair labelled UP. `prototype/plan.PROTOTYPE.json` groups both model files as the same plan. The original model is preserved.

The browser drawing view contains only the drawing and its permanent 1.5 m grid. Models have no page boundary. At 1:75, grid squares print at 20 mm. A movable reference origin identifies existing grid axes; moving it must preserve grid and geometry alignment.

The plan library now provides plan and level thumbnails, separate metadata editing, text/tag/date filters, date sorting, explicit Edit/Play links, and independent plan duplication. Nullable creation/edit/play dates preserve unknown history; authored level edits and meaningful play saves update the owning plan too. Characters are shared within a plan; exploration and drawing marks are independent per level. A drawing-only level-switching control remains unimplemented. Exploration visibility now has a throwaway prototype (`?fog=1`) with position/range observers, explicit sight blockers, door states, and persistent observation history and shared model revisions in a separate exploration file. Its current assumptions and unresolved details are recorded in the design notes and prototype README.

Reusable drawing components now implement six original families: bed, chair, wall door, hinged hatch, iris valve and crew console. Plan-owned definitions and independently positioned instances resolve through the same drawing, bounds, thumbnails, printing and remembered-fog paths. Following Referee evaluation, generic machinery is withdrawn from the usable catalogue and demo; legacy saved definitions remain renderable. Hatches have a hinge and handle, iris valves have circular contours, and dashed/up, solid/down or solid-plus-inner-dashed/both replace directional lettering. The revised standard bed is 1 × 2.25 m. A separate searchable catalogue exposes supported settings, placement/access advice and explicit sight semantics. Metre footprints and clearances are proposed defaults, not calibrated source dimensions or universal Traveller standards. The Referee identified Robert Pearce's Yet Another Traveller Blog as a reference; `catalog/pearce-symbols/` retains 2,185 source symbol images, 29 checked door/hatch meanings and 2,004 named CAD blocks, while `docs/research/component-inventory.md` describes 59 identifiable families. Original component artwork remains distinct from those references. Referee viability approval under ticket #13 is pending and gates later catalogue expansion; custom geometry and assemblies remain later scope.

Editing and play now have prototype modes: Shift-E switches between them. One thin icon toolbar shows in both modes, with sections that apply to the current mode: the first button is Play in Edit and Stop in Play, then file, design (Edit only), zoom and fog/range/character tools (Play only); character editing happens in a popup at the marker (⌘-click, or ⌘/Ctrl+Enter on a focused marker). Play is expected to use a fixed layout with exploration and no red reference axes; the grid remains. Binding play to a layout revision is a proposal, with the policy for adopting later edits still open.

## Documentation discipline

Record settled requirements in the design notes, terms in the glossary, and observed prototype lessons in the findings. Keep this file as a short entry point. Distinguish implemented behaviour, agreed requirements, and proposals. Update the relevant record when a correction or evaluation resolves something; screenshots and chat history alone are insufficient.

Play now supports saved named PC/NPC markers shared across levels within their owning plan. Add PC/NPC open a creation popup that requires a name (and a visual range for a PC; NPCs have none), and a ⌘-click popup at each marker edits its name, range and level and removes it; click a PC to select its POV/range and drag markers to move them. Only that PC reveals from movement destinations; NPCs obey current visibility and leave no remembered markers. Shift-F toggles fog for the GM's full-plan view. Reset keeps characters and pauses reveal. Manual level transfers are implemented; combat integration with `ceres.rounds` and automatic travel are deferred. See `prototype/README.md` for operations and `docs/prototype-findings.md` for checks and outstanding evaluation.
